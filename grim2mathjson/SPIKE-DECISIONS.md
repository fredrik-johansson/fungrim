## 1. `Where` + `Def` substitution (197 entries)

**Entries examined:** 2ae142 (plain Defs `q`, `w`), ff5e82 (function def
`a_(n) := ComplexDerivative(Sinc(z), For(z,z,n))/n!`), 6fce07 (recursive def
`a_(n) := Sqrt(2 + a_(n-1))`), 95fb3e / 08b69d / a2b0f9 (tuple destructuring
`Def(Tuple(a_(n), b_(n)), AGMSequence(n,a,b))`), 61480c (plain def).
Census: 143 entries plain-only, 20 with tuple defs, 41 with function defs,
**0 with Matrix2x2 defs**.

**Decision:**
- Plain `Def(x, val)`: substitute right-to-left via
  `Expr.replace({x: val}, semantic=True)`.
- `Def(Tuple(...), rhs)`: componentwise substitution iff rhs is a literal
  `Tuple`; otherwise skip-code **`where-def-tuple`**.
- Function defs `Def(f(z), body)`, body not referencing `f`: **beta-reduce at
  translation time** (replace each call `f(args)` with `body[z := args]`).
  This upgrades the plan's default-skip: the reduced forms box cleanly.
- Recursive function defs: skip-code **`where-recursive-def`**.

**Verification:**
```
# 1 PASS [2ae142] Where plain Defs q,w substituted (JacobiTheta r-deriv series)
# 1 PASS [ff5e82] Where function-def beta-reduced (a_(n) := D^n Sinc / n!)
# 1 PASS [(policy)] Apply(Function literal, arg) fallback for unreduced defs
```
Caveat discovered: a MathJSON call with a Function-literal head
`[["Function", body, "z"], arg]` **THROWS** in `ce.box()`
("The first element of an array should be a string"). If an unreduced function
value ever needs emitting, use `["Apply", ["Function", body, "z"], arg]`
(boxes; `["Apply",["Function",["Power","z",2],"z"],3]` evaluates to 9).

# 2 PASS [d0d03b] ComplexDerivative order r (symbolic, typed)
# 2 PASS [83065e] ComplexDerivative wrt 2nd argument

## 3. `Sum`/`Product` with bare `For(p)` + condition; DivisorSum/PrimeSum/…

**Entries examined:** 8f5e66 (PrimeProduct, bare `For(p)`), c33e2b /
ff190c (PrimeProduct/PrimeSum + `Divides` condition), 08ff0b (DivisorSum +
`Less` condition), aaef97 (DivisorSum no condition). Census: bare-`For`
appears **only** under PrimeSum/PrimeProduct/DivisorSum/DivisorProduct — plain
`Sum(body, For(p), cond)` does not occur.

**Decision:** CE's `canonicalIndexingSet` accepts the 3-arg Element condition
form (EL-3). Emit:
- `PrimeSum/PrimeProduct(f, For(p) [, cond])` →
  `["Sum"/"Product", f, ["Element", "p", "Primes" [, cond]]]` with shell
  `Primes: collection<integer>`.
- `DivisorSum/DivisorProduct(f, For(d, n) [, cond])` →
  `["Sum"/"Product", f, ["Element", "d", ["Divisors", n] [, cond]]]` with shell
  `Divisors: (integer) -> collection<integer>`.

**Verification:**
```
# 3 PASS [8f5e66] PrimeProduct(f, For(p)) Euler product
# 3 PASS [c33e2b] PrimeProduct with Divides condition (EL-3)
# 3 PASS [08ff0b] DivisorSum with Less condition (EL-3)
# 3 PASS [(semantics)] EL-3 evaluation semantics: Sum(d, d in 1..6, d<4) = 6
```
The EL-3 form has correct *evaluation* semantics, not just boxing:
`["Sum","d",["Element","d",["Range",1,6],["Less","d",4]]]` evaluates to **6**.
**Caveat:** the condition head must be **boolean-typed**. With `Divides`
undeclared, Element canonicalization emitted
`["Error",["ErrorCode","'incompatible-type'","''boolean''",...]]`. Fixed by
shell-declaring `Divides: (integer, integer) -> boolean` (likewise
`CongruentMod`). These predicate shells go in `declarations.json`.

## 5. Directed infinities; `UnsignedInfinity`/`Undefined` conventions

## 7. Subscripted/indexed variables (`z_(k)`, `Subscript(a, n)`)

**Entries examined:** 13f252 / 4cb707 (family calls `z_(k)`, `b_(k)`),
2a8ec9 (`Subscript(a, k)` symbolic index inside Sum), b9c36d
(`Subscript(e, k)`).

**Decision:**
- Family calls `z_(k)` keep **call form** `["z_", "k"]`, preserving the literal
  trailing-underscore Fungrim name (no normalization to `z` — avoids collision
  with sibling scalar variables). Entry annotated `indexedFamily: ["z_"]`.
- `Subscript(a, <literal int>)` → fused symbol `"a_1"` (CE canonicalizes this
  itself; round-trips).
- `Subscript(a, k)` with **symbolic** k → also call form `["a_", "k"]`
  (synthesized family head), because of the finding below.

**Verification & finding:**
```
# 7 PASS [13f252] family call z_(k) keeps call form (binding preserved)
# 7 PASS [2a8ec9] Subscript(a,k) symbolic index -> call form a_(k)
# 7 PASS [(literal)] Subscript with literal index -> fused symbol
(probe 3) Sum(["a_","k"], k=1..3) .evaluate() → a_(1) + a_(2) + a_(3)   ✓ binding kept
(probe 2) Sum(["Subscript","a","k"], k=1..3) canonical → ["Sum","a_k",…]
          .evaluate() → 3 * a_k                                          ✗ binding LOST
```
**CE discovery:** `["Subscript", sym, sym]` canonicalizes to a fused symbol
(`a_k`), silently severing the bond to a surrounding binder. The plan's
proposed `["Subscript", "z_", "k"]` encoding is therefore semantically unsafe
inside Sum/Product/For bodies; the call-form encoding is both safe and
verified (works even with the family head undeclared).

## 15. Name collisions: `RiemannZeta`→`Zeta`, `BetaFunction`→`Beta`, `Erf`, …

**Entries examined:** af23f7 (RiemannZeta), 591d64 (BetaFunction =
B(1/2,1/2) = π), 78fca3 (Erf), f8de2e (Erfc), 622772 (Erfi).
Arity census across the whole corpus: `RiemannZeta` is **1-arg in all 116
occurrences** (the live fungrim.org 2-arg derivative form does not occur in
this snapshot — derivatives are written via `ComplexDerivative` or
`HurwitzZeta(s,a,r)`); `BetaFunction` always 2-arg; `Erf`/`Erfc`/`Erfi`
always 1-arg.

**Decision (mappings verified, adopt):**
- `RiemannZeta` → `Zeta` (CE `(number) -> number`; `Zeta(2)` = π²/6 exact match).
- `BetaFunction` → `Beta` (CE `(number, number) -> number`; `Beta(2,3)` = 1/12
  and `Beta(1/2,1/2)` = π exact match).
- `Erf` → `Erf`, `Erfc` → `Erfc` (same mathematical function; see bug note).
- `Erfi`: no CE definition → verbatim + shell `(complex) -> complex`.
- `HurwitzZeta`: no CE definition → verbatim + shell
  `(complex, complex, integer?) -> complex` (3rd arg = derivative order).

**Verification:**
```
#15 PASS [af23f7/591d64/78fca3/622772] all four candidates box & round-trip
PASS Zeta(2) == pi^2/6        rel.err 0.00e+0
PASS Beta(2,3) == 1/12        rel.err 0.00e+0
PASS Beta(1/2,1/2) == pi      rel.err 0.00e+0
WARN Erf(1):  got 0.8427006897475899  expected 0.8427007929497149  rel.err 1.22e-7
WARN Erfc(1): got 0.15729931025241006 expected 0.15729920705028513 rel.err 6.56e-7
```
**CE bug found (does not block the mapping):** CE's `Erf`/`Erfc` numeric
kernel is only ~7-digit accurate (likely the classic Abramowitz–Stegun 7.1.26
rational approximation) and does **not** improve at `ce.precision = 30`
(still returns the machine-precision value). Any Fungrim numeric validation
involving Erf must use a tolerance ≥ 1e-6 until fixed; filed as a triage note
for the M5 harness / REVIEW.md numerics work.

## Cross-cutting findings (change the plan's assumptions)

1. **EL-3 condition form works and evaluates correctly** — the plan's open
   question §7.3 is resolved positively; no alternative encoding needed. But
   condition predicates must be boolean-typed ⇒ `Divides`, `CongruentMod`
   shells are *required*, not optional.
2. **Symbolic-order `Derivative` and 4-arg `JacobiTheta` require typed
   variables** ⇒ M5 `load.ts` must `ce.declare()` each entry's variables with
   a type inferred from its assumptions (default `complex`→`number` is enough
   for most; `integer` needed where the variable feeds an `integer?` slot).
3. **`Subscript` fuses symbolic indices into dead symbols** (binding loss) ⇒
   plan §2.3's `["Subscript", "z_", "k"]` encoding is replaced by call-form
   `["z_", "k"]` everywhere (open question §9.4 resolved: call form).
4. **n-ary chains pass through** (open question §9.6 resolved: rely on CE
   chain semantics; no pairwise expansion).
5. **Where function defs are beta-reducible** (open question §9.3 resolved:
   beta-reduce non-recursive defs; skip recursive ones). Direct
   Function-literal-head calls throw in `ce.box` — use `Apply` if ever needed.
6. **`Element(<untyped symbol>, <set>)` evaluates to `False`** in CE instead
   of staying unevaluated — assumption expressions must not be naively
   evaluated by the harness (record-only), and Phase-1 guard work needs this
   fixed or worked around.
7. **CE `Erf`/`Erfc` accuracy bug** (~1e-7 rel. err, precision-independent).
8. **Matrix2x2-in-Where doesn't exist** in the corpus; tuple-indexing sets are
   exactly 8 entries (skip); directed infinities 18 entries (flag, don't skip);
   `Undefined` appears in exactly 1 formula entry.
9. `ZZGreaterEqual(0|1)`/`ZZLessEqual(0)` map to CE's named integer sets
   (`NonNegativeIntegers`/`PositiveIntegers`/`NonPositiveIntegers`) rather than
   `Range` — better type integration than the plan's uniform `Range` mapping.
